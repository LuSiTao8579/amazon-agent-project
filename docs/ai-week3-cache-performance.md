## 如何解读这次测量

- 使用同一个测试管理员和同一个聊天会话，工具均串行执行。固定模型通过本地 HTTP 返回相同的工具名与参数。表中模型耗时只反映本地适配器和固定响应；线上厂商的网络与推理耗时需要在对应环境测量。
- 隔离测试库中，在既有 10 个用户和 7 家公司上增加 10,000 个用户与 20,000 家公司并更新数据库统计信息。用户查询按岗位和状态筛选，按姓名排序取第 2 页；公司查询筛选英国伦敦的等级 2、3；Dashboard 筛选英国、等级 2、3 和成立年份 2018–2020。
- 每个工具先预热两对，再测 24 对。冷样本在计时前使该工具维度的结果缓存失效，热样本保留相同结果。交替使用冷后热和热后冷的顺序。数据库和应用进程在整个测量中保持运行。
- 工具计时从注册中心进入到返回，包括权限复核、开关、DTO、缓存或业务查询以及审计。端到端计时从浏览器发送按钮的点击事件，到新回复的表格或报表节点进入布局并经过一次绘制机会。计数器逐次断言模型和工具各执行一次、冷查询执行一次业务读取、热查询执行零次。
- “其余链路”逐条用端到端耗时减去该次工具和模型耗时，再分别计算分位数。它包括会话持久化、代理、历史重新加载和浏览器工作。此处使用合计值。

## 缓存行为与边界

| 场景 | 验收结果 |
|---|---|
| 第二轮对话与会话过期 | 命中时读取上一轮上下文，历史加载方法调用为 0。将测试会话 TTL 缩至 1 秒并等待真实过期后，下一轮回源 PostgreSQL 一次，Redis 中按第一、第二、第三问的顺序读回消息。会话关闭清理缓存，用户和会话间的独立性由现有回归覆盖。 |
| 新请求重复查询 | 同一用户使用新 requestId，省略或显式给出默认分页、排序，调整等级数组顺序，取得相同公司表。新助手消息 ID 不同，每次新增一条审计，第二次业务列表调用增量为 0。 |
| 同一请求重试 | 同一会话、请求编号和文本重放已完成回合，返回原消息。模型、业务查询和工具审计增量均为 0。 |
| 改用户、条件或展示方式 | 不同用户、页码和等级分别查库。Dashboard 的综合报表、指标卡、等级单图和趋势单图各按对应参数返回。 |
| 撤权、禁用和异常 | 先查用户并形成缓存，再撤权，新回合得到 FORBIDDEN，历史和重放同样隐藏用户行。已缓存的公司工具被禁用后返回不可用，重新启用后可命中。业务异常后的同条件新请求重新进入 Service 并成功。 |
| 结果真实过期 | 对测试查询保留内容并把 TTL 缩至 1 秒。等到 Redis 查不到该条结果后重发，新请求重新调用业务 Service 一次，并返回相同内容。 |

结果缓存沿用 `ai:chat_cache:`，按认证用户和工具名隔离。键基于版本化结果格式和 DTO 校验后的条件生成，包含筛选、分页、实际排序及 Dashboard 展示选项。岗位、等级与图表按集合处理。默认 TTL 为 600 秒，可通过 `AI_CHAT_CACHE_POLICIES` 按 `query_users`、`query_companies`、`dashboard_metrics` 设置 `enabled` 和 `ttlSeconds`。这些工具的业务结果只依赖解析后的参数与当前权限，因此同一用户的等价查询可以跨会话复用。

业务数据发生变更时，已缓存结果可保留到 TTL 到期；已有的 `invalidateChatDimension` 支持业务写入方在提交后主动失效。修改公司数据会同时影响公司列表和 Dashboard 两个维度。权限和开关在每次新调用时重新检查。
