# 第一步：核对现状与确定字段

## 为什么先做这一步
页面新增字段必须有数据库和接口支持。先确定字段含义，能避免前后端各写一套规则。
2026-10-29 核对：已有 1 个用户，0001 用户表迁移；User/Company 是已鉴权的占位页。原有账号必须保留。

## 本次开发约定（不是 Leader 原文指定的细节）
- users 复用登录用户表，增加 name、role、status、is_admin。
- role 是岗位：Member / Manager / Analyst；一个人一个岗位，筛选器可同时选多个岗位。
- status 为 active / inactive；停用账号不能登录，已签发 JWT 也会在下一次请求中被拒绝。
- 管理权限与岗位分离，is_admin 只能由本地管理命令授予。注册不能选择管理权限。
- 用户列表及增改删仅管理员可访问；公司所有已登录用户可读、管理员可写。
- 管理员账号不允许在管理页面编辑/删除，避免误删自己或最后管理员。
- 新增 User 是创建可登录账号，管理员输入初始密码，仍用 Argon2id 哈希。没有邮件邀请或重置密码功能。
- 批量删除最多 100 个当前明确选择的普通用户，事务保证全成或全不成；切换筛选/页码清除选择。
- companies 按 CSV 八个字段保存。founded_year 是成立年份，不伪造供应日期。
- annual_revenue 是年营收；revenue / employees 是人均年营收，不是利润或风险评分。币种未给出，显示原始单位。
- 演示色阶为 <100、100–<500、>=500 原始单位/人，明确显示图例；员工数为0则不可计算。
- relationships 保留 company_code → parent_company；根节点 parent 为 NULL；不另做关系图。
- 有任何关系引用的公司禁止删除，返回409，不级联删除数据。
- 公司前端也提供新增/编辑/删除，使后端CRUD可以从页面验收。
- 角色、状态、色阶及业务词汇之后可按 Leader 确认统一调整。

## 六步提交顺序
1. 本文：现状、边界与规则。
2. 新增迁移：保留账号，扩展用户并建公司/关系表。
3. CSV导入与演示用户：严格校验、事务、幂等，不提交真实密码或本地数据文件。
4. User：受保护的CRUD API和MUI管理页面。
5. Company：CRUD API和折叠表格。
6. 回归测试、验收指南与学习索引。

## 学习提示
数据库 snake_case 与接口 camelCase 是命名习惯，不是两份不同数据。
注册/登录解决身份认证；is_admin 判断能否管理数据，是授权。
不要修改已执行的0001迁移。新变化写新迁移，其他开发者才能重现同样的结构。
原始CSV留在桌面，仓库只提交导入工具及合成测试，不将Leader附件自动公开。
